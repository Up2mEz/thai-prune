# เนื้อหาสไลด์: Typhoon OCR ยังอ่านภาษาไทยพลาดตรงไหน

เอกสารนี้บอกว่าแต่ละหน้าควรพูดอะไร ใส่ตัวเลขอะไร และควรมีภาพแบบไหน ส่วนภาพให้ทำเองตามคำอธิบาย

ทุกหน้าใช้โครงเดียวกัน:

- **คำถาม:** หน้านี้ตอบคำถามอะไร
- **ทำอะไร:** ทดลองอย่างไร (เล่าแบบคนไม่เคยเห็นงานก็เข้าใจ)
- **ผล:** ตัวเลขที่ต้องใส่
- **แปลว่า:** ประโยคที่อยากให้อาจารย์จำ
- **ภาพ:** ควรวาดอะไร
- **ต้องบอกด้วย:** ข้อจำกัดของหน้านั้น

---

## ก่อนเริ่ม: ตกลงคำที่ใช้ทั้ง deck

บนสไลด์จะใช้แค่คำเหล่านี้ และอธิบายครั้งแรกที่พูดถึง

| คำ | ความหมาย |
|---|---|
| **mark** | สระบน (ิ ี ึ ื ั ็), สระล่าง (ุ ู) และวรรณยุกต์ (่ ้ ๊ ๋) ซึ่งเป็นสิ่งที่งานนี้สนใจ |
| **Typhoon** | Typhoon OCR 1.5 ขนาด 2B เป็นโมเดลอ่านเอกสารไทยแบบเปิดที่ดีที่สุดตอนนี้ |
| **โมเดลตั้งต้น** | Qwen3-VL-2B เป็นโมเดลที่ Typhoon นำไป train ต่อ ใช้เทียบว่า Typhoon ดีขึ้นแค่ไหน |
| **CER** (Character Error Rate) | ตัวอักษร 100 ตัว ต้องแก้กี่ตัวถึงจะตรงเฉลย ยิ่งน้อยยิ่งดี |
| **คะแนน mark** | เอา mark ทุกตัวในเฉลยมาเทียบกับที่โมเดลเขียน โดยหักทั้งตัวที่หายไปและตัวที่เขียนเกินมา คะแนนเต็ม 100 ยิ่งมากยิ่งดี (ชื่อทางเทคนิคคือ F1 score) |
| **วนซ้ำ** | โมเดลเขียนคำเดิมซ้ำไม่หยุด เช่น "QMS QMS QMS …" จนถึงความยาวสูงสุด |
| **ชุดทดสอบ** | ThaiOCRBench ชุดทดสอบ OCR ภาษาไทยที่ทีม Typhoon สร้าง งานหลักคือ "อ่านทั้งหน้า" 69 หน้า |

**ตัวเลขทุกตัวในสไลด์:**
- ใช้คำสั่งที่เป็นคำถามของชุดทดสอบ
- ทดลองกับคำสั่งที่ Typhoon แนะนำในคู่มือด้วย ผลไปทางเดียวกัน จึงไม่ต้องใส่บนสไลด์ ยกเว้นหน้า 12

**ป้ายเล็กมุมล่างทุกหน้าที่มีผล:** "ผลเบื้องต้น · ข้อมูลที่ใช้ออกแบบวิธี · ยังไม่ได้ยืนยันกับข้อมูลชุดที่เก็บไว้"

**ความยาว:** 13 หน้า ใช้เวลาราว 15–20 นาที

## หน้า 1: วรรณยุกต์ไม่ใช่จุดอ่อนของ Typhoon แล้วอะไรคือจุดอ่อน

- **ภาพ:** หน้าเอกสารไทยจริงหนึ่งหน้า หรือไม่ใส่ภาพ
- **พูด:** ทำร่วมกับเพื่อน (PELY334) เพื่อนรับเรื่องความเร็ว และเรื่องวิธีบังคับให้โมเดลดูภาพมากขึ้น

## หน้า 2: ทำไมเลือก Typhoon

- **คำถาม:** ทำไมไม่ทำกับโมเดลอื่น
- **เนื้อหา:**
  - Typhoon เป็น OCR ภาษาไทยแบบเปิดที่ดีที่สุดตอนนี้ คนใช้จริง
  - ถ้าลดจุดพลาดที่เหลือได้ ผลจะไปถึงผู้ใช้ทันที
- **เงื่อนไขที่ตั้งไว้ (กล่อง 3 กล่อง):**
  1. ไม่ train โมเดลเพิ่ม ปรับแค่วิธีใช้งาน
  2. ช้าลงได้นิดหน่อย แต่ห้ามช้าลงมาก
  3. ต้องดีกว่าวิธีใช้งานแบบปกติอย่างวัดได้
- **พูด:** งานนี้เปลี่ยนทิศจากงานเดิมเรื่องการตัดข้อมูลภาพ (token pruning) มาแก้จุดพลาดของโมเดลที่ใช้งานจริง

## หน้า 3: อ่านสลับบรรทัด ไม่ควรนับว่าอ่านผิด

- **คำถาม:** วิธีวัดแบบเดิมวัดสิ่งที่เราสนใจได้จริงไหม
- **ปัญหาที่เจอ:**
  - วิธีวัดเดิมเทียบข้อความแบบเรียงตามลำดับ
  - ถ้าโมเดลอ่านกล่องข้อความขวาก่อนกล่องซ้าย ทั้งที่อ่านถูกทุกตัว วิธีเดิมจะนับว่าผิดเยอะ
  - บางหน้า CER เกิน 100% เพราะเหตุนี้และเพราะการวนซ้ำ
- **ทำอะไร:** สร้าง "คะแนน mark" ที่ไม่สนลำดับบรรทัด แต่ยังหักคะแนนเมื่อ mark หายหรือเขียนเกิน
- **ผล:**
  - คะแนน mark ของ Typhoon แบบไม่สนลำดับ = **94.9**
  - ถ้าบังคับให้ตรงลำดับ = 93.1
  - ส่วนต่างราว 2 คะแนน มาจากลำดับการอ่านอย่างเดียว ไม่ใช่การอ่านผิด
- **ภาพ:** ตัวอย่างจริงหนึ่งชุด
  - ซ้าย: เฉลยมีบรรทัด A แล้ว B
  - ขวา: โมเดลอ่าน B แล้ว A
  - ใต้ภาพ: "วิธีเดิม: ผิดเยอะ / วิธีใหม่: ถูกครบ"

## หน้า 4: ถ้าอ่านพยัญชนะถูก วรรณยุกต์ผิดแค่ 1 ใน 150

- **คำถาม:** Typhoon เก่งแค่ไหน เมื่อเทียบกับโมเดลตั้งต้น
- **ทำอะไร:** ให้ทั้งสองโมเดลอ่านเอกสาร 69 หน้าแบบปกติ แล้ววัดผล
- **ผล (การ์ดตัวเลข 4 ใบ เทียบสองโมเดล):**

| | Typhoon | โมเดลตั้งต้น |
|---|---|---|
| CER ของหน้าทั่วไป (ค่ากลาง) | **2.8%** | 27.1% |
| คะแนน mark | **94.9** | 41.0 |
| วรรณยุกต์ผิด ในตำแหน่งที่อ่านพยัญชนะถูก | **0.65%** | 9.4% |
| หน้าที่วนซ้ำจนต้องตัด | **2.9%** | 43.5% |

- **แปลว่า:**
  - Typhoon ดีกว่าโมเดลตั้งต้นมาก
  - แถวที่สามสำคัญที่สุด: ตรงไหนที่ Typhoon อ่านพยัญชนะถูก มันใส่วรรณยุกต์ผิดแค่ราว 1 ใน 150 ตัว
  - วรรณยุกต์ที่ผิดส่วนใหญ่จึงมากับความผิดอย่างอื่น เช่น อ่านผิดทั้งคำ หรือไม่ได้อ่านบรรทัดนั้นเลย
- **ภาพ:** การ์ดตัวเลขใหญ่ 4 ใบ ไม่ใช้กราฟแท่ง เพราะแต่ละค่าใช้สเกลต่างกันมาก

## หน้า 5: ที่พลาดส่วนใหญ่คือไม่ได้อ่าน ไม่ใช่อ่านผิด

- **คำถาม:** mark ราว 6% ที่ Typhoon ยังพลาด พลาดเพราะอะไร
- **ทำอะไร:** ไล่ดู mark ที่พลาดทุกตัว แล้วแยกตามสาเหตุ
- **ผล (คิดเป็น % ของ mark ทั้งหมด):**

| สาเหตุ | % | ความหมาย |
|---|---|---|
| อ่านแล้ว แต่ไปอยู่คนละตำแหน่งกับเฉลย | 1.6 | ไม่ใช่ความผิดจริง |
| ทั้งบรรทัดหายไป | 2.3 | **มากที่สุด** |
| หายไปบางช่วงในบรรทัด | 0.7 | |
| อ่าน mark ผิดตัว | 1.5 | |

- **แปลว่า:**
  - ที่พลาดมากที่สุดคือโมเดลไม่ได้อ่านบรรทัดนั้นเลย
  - เมื่อเปิดดูทีละหน้า บรรทัดที่หายส่วนใหญ่ไม่ใช่เนื้อความ แต่เป็นข้อความในกราฟ, infographic, โฆษณาที่แทรก และหัวกระดาษ
  - ตรงกับที่ทีม Typhoon เขียนไว้ใน paper ว่า infographic เป็นจุดที่อ่อนที่สุด
- **ภาพ:**
  - แถบยาวแถบเดียว แบ่งสีตาม 4 สาเหตุ (สีเทาสำหรับ "คนละตำแหน่ง")
  - ข้างกันใส่หน้าเอกสารจริงหนึ่งหน้า ไฮไลต์ส่วนที่ Typhoon ข้าม
- **ต้องบอกด้วย:** การแยกสาเหตุใช้โปรแกรมตัดสินตามกฎ ไม่ได้ให้คนตรวจทุกจุด

## หน้า 6: ปิดภาพไปเลย ก็ยังเดาวรรณยุกต์ถูก 99%

- **คำถาม:** ตอนเลือกวรรณยุกต์ โมเดลดูจากภาพ หรือเดาจากคำรอบข้าง
- **ทำอะไร:**
  - ป้อนข้อความที่ถูกให้โมเดลจนถึงก่อนวรรณยุกต์ แล้วถามว่าวรรณยุกต์ตัวต่อไปควรเป็นตัวไหน
  - ทำสองแบบ: ให้เห็นภาพ และไม่ให้เห็นภาพ
- **ผล (% ที่เลือกวรรณยุกต์ถูก):**

| | เห็นภาพ | ไม่เห็นภาพ |
|---|---|---|
| Typhoon | 99.7 | 98.8 |
| โมเดลตั้งต้น | 98.1 | 98.9 |

- **แปลว่า:**
  - แค่รู้คำก่อนหน้า โมเดลก็เดาวรรณยุกต์ถูกเกือบทุกครั้งโดยไม่ต้องดูภาพ เพราะคำไทยส่วนใหญ่มีวรรณยุกต์ที่เป็นไปได้ไม่กี่แบบ
  - ภาพช่วย Typhoon ได้นิดหน่อย (+0.9) แต่ไม่ช่วยโมเดลตั้งต้นเลย
  - ความผิดจริงจึงเกิดตั้งแต่ก่อนถึงวรรณยุกต์ เช่น อ่านคำก่อนหน้าผิด หรือข้ามบรรทัด
  - เราเคยตั้งสมมติฐานว่าโมเดลที่ train มาเฉพาะทางจะดูภาพน้อยลง ผลกลับตรงข้าม Typhoon ดูภาพมากกว่า
- **ภาพ:** กราฟแท่งคู่ สองโมเดล โมเดลละสองแท่ง (เห็นภาพ / ไม่เห็นภาพ) แกนตั้งเริ่มที่ 95% และเขียนกำกับไว้ว่าไม่ได้เริ่มที่ 0
- **ต้องบอกด้วย:** การทดลองนี้ป้อนคำก่อนหน้าที่ถูกให้เสมอ ซึ่งตอนใช้งานจริงไม่ได้เป็นแบบนั้น

## หน้า 7: บังคับให้ดูภาพมากขึ้น วรรณยุกต์กลับพัง

- **คำถาม:** มีงานวิจัยที่แก้โมเดลด้วยการ "ลดการเดาจากภาษา บังคับให้ดูภาพมากขึ้น" วิธีนี้ช่วยภาษาไทยไหม
- **ทำอะไร (ของเรา):** ค่อย ๆ หักส่วนที่โมเดลเดาได้โดยไม่ดูภาพออกจากคะแนน แล้ววัดว่าเลือกวรรณยุกต์ถูกกี่ %
- **ผลของเรา (Typhoon):**

| หักส่วนที่เดาจากภาษา | เลือกวรรณยุกต์ถูก |
|---|---|
| ไม่หัก | 99.7% |
| หักครึ่งหนึ่ง | 97.3% |
| หักเต็ม | 42.3% |

- **ผลของเพื่อน (ใช้วิธีจาก paper จริงกับการอ่านทั้งหน้า):**
  - วิธี M3ID หยุดการวนซ้ำของโมเดลตั้งต้นได้ 6 จาก 7 หน้า
  - แต่วรรณยุกต์ผิดเพิ่มจาก 3.7% เป็น 7.6% และวรรณยุกต์หายไปเพิ่มจาก 18 เป็น 37 ตัว
  - เพื่อนลองกันไม่ให้วิธีนี้แตะ mark ความเสียหายลดได้แค่ครึ่ง และช้าลง 1.6 เท่า
- **แปลว่า:** การเดาจากภาษาเรื่องวรรณยุกต์ถูกอยู่แล้วเกือบทุกครั้ง การหักมันออกจึงหักคำตอบที่ถูกไปด้วย ผลของเราและของเพื่อนไปทางเดียวกัน
- **ภาพ:** กราฟเส้นของ Typhoon แกนนอนคือ "หักมากขึ้น" แกนตั้งคือ "% เลือกวรรณยุกต์ถูก" เส้นตกลงชัดเจน

## หน้า 8: ไม่กี่หน้าที่วนซ้ำ ก่อความผิดเกือบสามในสี่

- **คำถาม:** การวนซ้ำเสียหายแค่ไหน
- **ผล:**
  - 11 จาก 356 ครั้งที่ให้โมเดลอ่าน เกิดการวนซ้ำ
  - mark ที่ Typhoon เขียนเกินมาทั้งหมด **68–76% มาจากหน้าที่วนซ้ำแค่ 2–5 หน้า**
  - ถ้าไม่มีหน้าวนซ้ำเลย คะแนน mark จะขึ้นจาก 94.9 เป็น 97.4
- **แปลว่า:** การวนซ้ำเกิดไม่บ่อย แต่เกิดทีไรก็เสียหายมาก และแก้ได้โดยไม่ต้องไปยุ่งกับหน้าที่อ่านปกติ
- **ภาพ:**
  - ซ้าย: ภาพตัดข้อความจริงที่วนซ้ำ "QMS QMS QMS …"
  - ขวา: ตัวเลขใหญ่ "2–5 หน้า → 68–76% ของ mark ที่เกิน"
- **ต้องบอกด้วย:** 97.4 เป็นเพดานที่คิดจากการตัดหน้าวนซ้ำทิ้งทั้งหน้า ไม่ใช่ผลของวิธีใด

## หน้า 9: ห้ามซ้ำไม่ได้ผล ต้องหยุดให้ทัน

- **คำถาม:** วิธีไหนแก้การวนซ้ำได้ โดยไม่ทำหน้าที่อ่านปกติเสีย
- **ทำอะไร:** ลอง 3 วิธีกับเอกสาร 69 หน้า แล้วดูคะแนน mark ที่เปลี่ยนไปจากการอ่านแบบเดิม 2 มุม คือ ดูทุกหน้า และดูเฉพาะหน้าที่ไม่วนซ้ำ

| วิธี | ทำอะไร | ทุกหน้า | เฉพาะหน้าที่ไม่วนซ้ำ | หน้าที่ไม่วนซ้ำถูกเปลี่ยนคำตอบ |
|---|---|---|---|---|
| ลงโทษคำที่เคยเขียน (ค่าที่ทีม Typhoon ตั้งไว้ในโปรแกรม) | ลดโอกาสเขียนคำที่เคยเขียนแล้ว | +0.9 | **−1.3** | **100%** |
| ห้ามวลีซ้ำ (วิธีของ DeepSeek-OCR) | ห้ามเขียนวลีเดิมซ้ำ | −0.7 | 0.0 | 1.5% |
| **หยุดทันทีเมื่อเจอการวนซ้ำ** | พอข้อความเดิมซ้ำติดกันหลายรอบ (6–8 รอบ) ให้หยุดแล้วตัดส่วนที่ซ้ำทิ้ง | **+0.8** | **0.0** | **0%** |

- **ผลเพิ่ม:**
  - การลงโทษคำซ้ำได้คะแนนรวมเพิ่ม เพราะแก้หน้าที่วนซ้ำได้ แต่ไปเปลี่ยนคำตอบของทุกหน้า และทำหน้าปกติเสีย 1.3 คะแนน
  - ถ้าใช้คำสั่งของ Typhoon การลงโทษคำซ้ำทำให้คะแนนรวมลดลง 1.2
  - ในงานอ่านข้อความสั้น การลงโทษคำซ้ำทำให้วรรณยุกต์ผิดเพิ่มจาก 17.1% เป็น 22.6% (น่าจะเพราะข้อความไทยมีคำซ้ำเป็นปกติ)
  - ส่วนวิธีหยุดทำให้คะแนน mark ของงานอ่านข้อความสั้นขึ้น +3.3 และทำให้โมเดลเขียนสั้นลง 11% จึงเสร็จเร็วขึ้นด้วย
- **แปลว่า:**
  - การห้ามวลีซ้ำแก้ไม่หมด เพราะโมเดลเปลี่ยนไปวนแบบเพี้ยนนิดหน่อยแทน เช่น "ซอยจุฬาภรณ์ → ซอยนวมินทร์ → ซอยนวบินิต"
  - การลงโทษคำซ้ำแก้หน้าที่เสีย แต่ไปทำหน้าที่ดีอยู่แล้วให้แย่ลง
  - วิธีหยุดได้คะแนนเพิ่มพอ ๆ กัน โดยไม่แตะหน้าปกติเลย ระบบ OCR อื่น (Nougat, PaddleOCR-VL) ก็ใช้วิธีนี้
- **ภาพ:** กราฟแท่งแนวนอนแบบคู่ (ดูส่วน "วิธีทำกราฟ")
  - แต่ละวิธีมีสองแท่ง คือ "ทุกหน้า" และ "เฉพาะหน้าที่ไม่วนซ้ำ"
  - มีเส้น 0 ตรงกลาง แท่งที่ติดลบอยู่ซ้าย และแท่งที่เป็นบวกอยู่ขวา
- **ต้องบอกด้วย:**
  - จำนวนรอบที่ใช้ตัดสินว่า "วนซ้ำ" ตั้งหลังจากเห็นผลรอบก่อนแล้ว
  - หน้าที่วนซ้ำมีน้อย ช่วงความเชื่อมั่นของคะแนนรวมทุกวิธีจึงคร่อม 0 ยังสรุปทางสถิติไม่ได้
  - ต้องยืนยันกับข้อมูลชุดที่เก็บไว้

## หน้า 10: เร็วขึ้น 15% โดยคำตอบแทบไม่เปลี่ยน (งานของเพื่อน)

- **คำถาม:** ทำให้ Typhoon เร็วขึ้นได้ไหม โดยคำตอบไม่เปลี่ยน
- **ทำอะไร:** ใช้ speculative decoding คือให้โปรแกรมเดาคำถัดไปล่วงหน้าหลายคำ แล้วให้ Typhoon ตรวจรวดเดียว ถ้าเดาถูก Typhoon ไม่ต้องเขียนทีละคำ
- **ผล:**
  - Typhoon **เร็วขึ้น 1.14–1.15 เท่า**
  - คำตอบเหมือนเดิมทุกตัวอักษร 89–93% ของหน้า
  - หน้าที่ต่าง ต่างเฉพาะจุดที่สองตัวเลือกคะแนนเกือบเท่ากันอยู่แล้ว ซึ่งเป็นเรื่องการปัดเศษของการคำนวณ ไม่ใช่วิธีนี้ทำให้อ่านแย่ลง
- **แปลว่า:** ถ้าใช้คู่กับวิธีหยุดเมื่อวนซ้ำ น่าจะได้ทั้งผิดน้อยลงและเร็วขึ้น ซึ่งตรงกับเงื่อนไขที่ตั้งไว้
- **ภาพ:** การ์ดตัวเลข 2 ใบ: "เร็วขึ้น 15%" และ "คำตอบเหมือนเดิม 9 ใน 10 หน้า"
- **ต้องบอกด้วย:** ยังไม่เคยรันสองวิธีนี้พร้อมกันจริง คำว่า "ได้ทั้งสองอย่าง" ยังเป็นการคาดการณ์

## หน้า 11: โมเดลรู้ว่าตรงไหนไม่ชัด แต่แก้เองไม่ได้

- **คำถาม:** ถ้าโมเดลอ่านผิด มันรู้ตัวไหม
- **ทำอะไร:**
  - ทุกครั้งที่โมเดลเขียนตัวอักษร มันมีคะแนนความมั่นใจของตัวนั้นอยู่แล้ว
  - เราดูว่าจุดที่มั่นใจต่ำคือจุดที่อ่านผิดหรือไม่
- **ผล:**
  - ชี้ 5% ของจุดที่มั่นใจน้อยที่สุด จะเจอ mark ที่อ่านผิด **67–72%** ของทั้งหมด
  - ในจุดที่ชี้ไป มีผิดจริงราว 13 จาก 100 ขณะที่ทั้งหน้ามีผิดแค่ 1 จาก 100
- **ลองแก้:**
  - ให้โมเดลเปลี่ยนไปใช้ตัวเลือกอันดับสองของมันเอง ตรงจุดที่ไม่มั่นใจ คะแนนแทบไม่เปลี่ยน
  - ต่อให้รู้เฉลยแล้วเลือกตัวเลือกที่ถูกให้ทุกครั้ง ก็แก้ได้แค่ 17–29%
- **แปลว่า:** โมเดลรู้ว่าตรงไหนไม่ชัด แต่คำตอบที่ถูกไม่ได้อยู่ในตัวเลือกของมัน เพราะส่วนใหญ่ผิดทั้งคำ ไม่ได้ผิดแค่วรรณยุกต์ตัวเดียว ต้องกลับไปดูภาพตรงนั้นใหม่
- **ภาพ:** กรวย 3 ชั้น: "จุดทั้งหมด → 5% ที่ไม่มั่นใจ → จับ mark ที่ผิดได้ 7 ใน 10"

## หน้า 12: ซูมแล้วอ่านถูกขึ้น แต่ใช้เวลาเพิ่มเกินเท่าตัว

- **คำถาม:** ถ้าให้โมเดลดูภาพตรงจุดที่ไม่มั่นใจอีกครั้ง จะแก้ได้ไหม
- **ทำอะไร (ขั้นแรก, 21 หน้า):**
  - ตัดหน้าเอกสารเป็น 3 แถบแนวนอน ให้โมเดลอ่านแต่ละแถบใหม่ แล้วดูเฉพาะจุดที่มันไม่มั่นใจ
  - มีจุดที่อ่านผิด 40 จุด และจุดที่อ่านถูกแต่ไม่มั่นใจ 280 จุด

| อ่านใหม่ด้วย | จุดที่ผิด แก้ให้ถูกได้ | จุดที่ถูก ทำให้ผิด |
|---|---|---|
| ภาพเดิมทุกอย่าง (ไว้ดูว่าการวัดคลาดเคลื่อนเองแค่ไหน) | 0% | 4% |
| 3 แถบ ขนาดเดิม | 30% | 16% |
| **3 แถบ ขยาย 1.85 เท่า** | **50%** | **6%** |

- **ผลขั้นแรก:** การขยายภาพช่วยจริง แก้ได้ครึ่งหนึ่งของจุดที่ผิด และทำพังน้อย
- **ทำอะไร (ขั้นสอง, ครบ 69 หน้า):** สร้างเป็นวิธีเต็มที่ใช้ได้โดยไม่รู้เฉลย แล้ววัดกับเงื่อนไขที่เขียนไว้ก่อนรัน

| เงื่อนไขที่เขียนไว้ก่อนรัน | ผลที่ได้ | |
|---|---|---|
| คะแนน mark ต้องสูงขึ้น ทั้งสองแบบคำสั่ง | สูงขึ้นเล็กน้อย +0.15 และ +0.08 | ผ่าน |
| คำที่แก้ถูก ต้องมีอย่างน้อยสองเท่าของคำที่แก้แล้วพัง | แก้ถูก 35 คำ แก้พัง 17 คำ | ผ่าน |
| CER ต้องไม่แย่ลง | คำสั่งหนึ่งดีขึ้น อีกคำสั่งแย่ลงน้อยมาก (12.419% → 12.424%) | ไม่ผ่าน แต่ต่างกันจนแทบไม่มีความหมาย |
| เวลาทั้งหมดต้องไม่เกิน 1.5 เท่าของการอ่านปกติ | ใช้เวลา **2.4–2.8 เท่า** | **ไม่ผ่าน และเป็นปัญหาหลัก** |

- **แปลว่า:**
  - วิธีนี้แก้ถูกมากกว่าแก้พัง และผลยังไปทางเดียวกันใน 48 หน้าที่ไม่ได้ใช้ตอนออกแบบ
  - แต่ช้าเกินไป เพราะแต่ละหน้ามีบรรทัดที่โมเดลไม่มั่นใจราว 18 บรรทัด กระจายทั่วหน้า เลยต้องอ่านใหม่เกือบทั้งหน้า
  - ทางที่น่าจะไปต่อได้คือหาให้เจอว่าบรรทัดนั้นอยู่ตรงไหนในภาพ แล้วอ่านใหม่แค่บรรทัดนั้น
- **ตัวอย่างจริงที่ใส่ได้:**
  - แก้ถูก: "มีสติ → นิสิต", "ล่ม → เล่ม"
  - แก้พัง: "คุณ → ขอบคุณ"
- **ภาพ:**
  - ซ้าย: กราฟแท่งคู่ 3 กลุ่ม แต่ละกลุ่มมีแท่งเขียว "แก้ถูก" และแท่งแดง "ทำพัง"
  - ขวา: ตาราง 4 เงื่อนไข มี ✔ ✘

## หน้า 13: หาไม่เจอ กับ อ่านไม่ชัด ต้องแก้คนละแบบ

- **คำถาม:** ข้อความที่หายไปทั้งบรรทัด (หน้า 5) แก้ได้ด้วยวิธีเดียวกับการอ่าน mark ผิดไหม
- **ผล 3 การทดลอง:**

| ปัญหา | ตัดภาพให้เล็กลง | ขยายภาพ |
|---|---|---|
| **บรรทัดที่หายไปจากการอ่านทั้งหน้า** (21 หน้า) | อ่านทั้งหน้าใหม่ได้กลับมา 51% ถ้าตัดเป็น 3 แถบ ได้กลับมา **59%** | ไม่ได้เพิ่มเลย |
| **ข้อความในกรอบที่ถูกถาม** (งานของเพื่อน, 69 ข้อ) | ให้ทั้งหน้า Typhoon หาเจอ 7% ถ้าตัดเฉพาะกรอบให้ หาเจอ **99%** | – |
| **mark ที่อ่านผิด** (จากหน้า 12) | แก้ได้ 30% | แก้ได้ **50%** |

- **แปลว่า:**
  - ข้อความที่หาย ปัญหาคือโมเดล **หาไม่เจอ** การตัดภาพให้เล็กลงช่วยให้หาเจอ ส่วนการขยายภาพไม่ช่วย
  - mark ที่อ่านผิด ปัญหาคือ **มองไม่ชัด** การขยายภาพช่วย
  - งานของเพื่อนยืนยันอีกทาง: คำที่ Typhoon หาเจอตั้งแต่ตอนเห็นทั้งหน้า พอให้ดูเฉพาะกรอบ วรรณยุกต์ที่ถูกก็ยังถูกเกือบทั้งหมด (29 จาก 30 ตัว) และไม่มีวรรณยุกต์ที่ผิดตัวไหนกลับมาถูก แปลว่าเมื่อหาเจอแล้ว Typhoon ก็อ่านวรรณยุกต์ได้ดีอยู่แล้ว
- **ข้อเสียที่เจอ:** ถ้าตัดทุกหน้าเป็น 3 แถบเป็นวิธีปกติ คะแนน mark ลดจาก 95.3 เหลือ 88.5 เพราะย่อหน้าถูกตัดขาดตรงรอยต่อแถบ ต้องตัดตามโครงหน้าเอกสาร ไม่ใช่ตัดเท่า ๆ กัน
- **ภาพ:** ตาราง 3 แถว × 2 คอลัมน์ ช่องที่ได้ผลระบายสีเขียว
- **ต้องบอกด้วย:**
  - การทดลองบรรทัดที่หายมีแค่ 21 หน้า ตัวเลข +8 จึงยังไม่แน่นอนมาก
  - คำที่หาเจอตั้งแต่ทั้งหน้ามีแค่ราวหนึ่งในสามของข้อ และอาจเป็นข้อที่ง่ายกว่า
  - แต่ละแถวมาจากชุดข้อมูลคนละชุด ห้ามเทียบตัวเลขข้ามแถว

### library ที่เลือกได้

ตอนนี้โปรเจกต์ยังไม่ได้ติดตั้ง library ทำกราฟตัวไหนเลย (ตรวจแล้ว)

| library | จุดเด่น | ข้อควรระวัง | ใช้เมื่อ |
|---|---|---|---|
| **Plotly** + Kaleido (ตัว export รูป) | browser เป็นตัววางตัวอักษร จึงวาง mark ที่ซ้อนกันได้ถูกที่ (เช่น "ที่", "ปั้น") และ export ได้ทั้ง SVG, PNG, PDF | Kaleido รุ่น 1 ขึ้นไปต้องมี Chrome ในเครื่อง และต้องตั้ง template เป็น `simple_white` เพื่อเอาพื้นหลังสีเทาออก | **แนะนำ** สำหรับทุกกราฟที่มีภาษาไทยบนแกนหรือบนแท่ง |
| **matplotlib** | เป็นมาตรฐาน ปรับได้ทุกจุด | ไม่จัดตำแหน่งตัวอักษรซ้อน ซึ่งภาษาไทยต้องใช้เมื่อมี mark สองชั้น (สระบนกับวรรณยุกต์) จึงอาจวางทับกัน งานนี้พูดเรื่อง mark โดยตรง ถ้ากราฟแสดง mark ผิดจะเสียความน่าเชื่อถือทันที มีทางแก้สองทาง: ใช้ backend `mplcairo` ที่จัดตัวอักษรได้ หรือให้รูปมีแต่ตัวเลข แล้วพิมพ์ภาษาไทยในโปรแกรมสไลด์ | กราฟที่ไม่มีภาษาไทยในรูป |
| **seaborn** | ต่อยอดจาก matplotlib ทำกราฟสถิติได้เร็ว | มีปัญหาภาษาไทยแบบเดียวกับ matplotlib | ไม่จำเป็นสำหรับงานนี้ เพราะกราฟไม่ซับซ้อน |
| **Altair** (Vega-Lite) | เขียนสั้น ข้อความวาดใน browser เหมือน Plotly | export รูปต้องใช้ `vl-convert` และปรับรายละเอียดได้น้อยกว่า Plotly | ทางเลือกแทน Plotly |
| **plotnine** | เขียนแบบ ggplot2 ของ R | ใช้ matplotlib อยู่ข้างใต้ จึงมีปัญหาภาษาไทยแบบเดียวกัน | ถ้าถนัด R |

**ติดตั้งแบบไม่แก้ไฟล์ของโปรเจกต์:** รันสคริปต์กราฟด้วยคำสั่งนี้ (`make_figures.py` เป็นชื่อตัวอย่าง)

