ชุดนี้ทำตามต้นฉบับ paper (`docs/paper/ieee/v2/`, ชื่อเรื่อง *Are Tone Marks the Weak Point of Open Thai OCR? A Locked-Split Study of Eight Models*) และ `docs/CLAIMS.md` ข้อ 12–17 ไม่ใช่การแก้เด็คเดิมใน `docs/presentdesign.md`

## เรื่องที่เล่าทั้งเด็ค (เส้นเรื่องเดียว)

> วรรณยุกต์และสระของไทยตัวเล็กและเปลี่ยนความหมายคำได้ คนจึงสงสัยว่าเป็นจุดอ่อนของ OCR ภาษาไทย เราวัดใน 8 โมเดลแบบเปิดแล้วพบว่า **ส่วนใหญ่ไม่ใช่** mark ที่เสียไปส่วนใหญ่ไม่ได้ถูกอ่านผิด แต่ **ไม่ปรากฏใน output เลย** (ข้ามบรรทัด หาไม่เจอ หรือวนซ้ำ) เมื่อให้บริบทถูก โมเดลเลือกวรรณยุกต์ถูกราว 99% ส่วนวิธีที่ช่วยได้ง่ายที่สุดคือหยุดเมื่อวนซ้ำ ซึ่งยืนยันบนชุดข้อมูลที่เปิดอ่านครั้งเดียว

## ก่อนเริ่ม: ตกลงคำที่ใช้ทั้ง deck

| คำ                        | ความหมาย                                                                                                                             |
| ------------------------- | ------------------------------------------------------------------------------------------------------------------------------------ |
| **mark**                  | สระบน (ิ ี ึ ื ั ็), สระล่าง (ุ ู) และวรรณยุกต์ (่ ้ ๊ ๋)                                                                            |
| **คะแนน mark**            | เอา mark ทุกตัวในเฉลยมาเทียบกับที่โมเดลเขียน หักทั้งตัวที่หายและตัวที่เขียนเกิน เต็ม 100 (ชื่อทางเทคนิคคือ mark F1) ไม่สนลำดับบรรทัด |
| **ไม่ปรากฏใน output**     | บรรทัดหรือช่วงข้อความในเฉลยที่หาไม่เจอในสิ่งที่โมเดลเขียน **ไม่ได้แปลว่าโมเดลมองไม่เห็น** (อาจเห็นแล้วไม่เขียน)                      |
| **วนซ้ำ (loop)**          | โมเดลเขียนหน่วยเดิมซ้ำไม่หยุดจนถึงความยาวสูงสุด                                                                                      |
| **หยุดเมื่อวนซ้ำ (stop)** | ตัด output ตั้งแต่สำเนาแรกของหน่วยที่ซ้ำ 8 ครั้ง (หรือ 6 ครั้งถ้าหน่วยยาว 50 ตัวอักษรขึ้นไป) ไม่ต้อง train เพิ่ม                     |
| **ชุด calibration**       | 178 ข้อ (อ่านทั้งหน้า 69, อ่านข้อความสั้น 109) ใช้พัฒนาวิธีและตัดสินใจออกแบบ                                                         |
| **ชุด locked**            | 352 ข้อ (อ่านทั้งหน้า 128, อ่านข้อความสั้น 224) ไม่แตะจนกฎทุกข้อนิ่ง แล้วเปิดอ่าน **ครั้งเดียว** ตามที่ลงทะเบียนไว้ล่วงหน้า          |
| **forced choice**         | ให้ข้อความที่ถูกต้องจนถึงตำแหน่ง mark แล้วให้โมเดลให้คะแนนตัวเลือก mark ที่เป็นไปได้ ไม่ใช่การเขียนเอง                               |
| **Thai fine-tune**        | Typhoon OCR 1.5 และ Pathumma-llm-vision 3.0 (ทั้งคู่ train ต่อจาก Qwen3-VL-2B)                                                       |
| **โมเดลทั่วไป**           | Qwen3-VL-2B (ตั้งต้น), Qwen3-VL-4B, SEA-LION v4 4B                                                                                   |

**ป้ายเล็กมุมล่างทุกหน้าที่มีผล (สองแบบ):**
- ผลบน calibration: "ผลเบื้องต้น · ชุด calibration (ใช้ออกแบบวิธี)"
- ผลบน locked: "ผลเบื้องต้น · ชุด locked อ่านครั้งเดียว · ไม่ใช่หลักฐานผ่าน gate"

**ถ้ามีทั้งตัวเลข calibration และ locked ให้ใช้ locked เป็นตัวเลขหลัก**

# ส่วน 1: ชื่อเรื่อง และ Introduction (สไลด์ 1–3)

## สไลด์ 1: ชื่อเรื่อง

- **บนสไลด์:** *Are Tone Marks the Weak Point of Open Thai OCR? A Locked-Split Study of Eight Models* / "วรรณยุกต์เป็นจุดอ่อนของ OCR ภาษาไทยแบบเปิดจริงหรือ" / ผู้เขียน 3 คนและสังกัด / 
- **พูด:** "งานนี้ทำร่วมกับเพื่อน (PELY334) เพื่อนรันการทดลองบน GPU ส่วนเรื่องวิธีวัดและการเขียน paper เป็นส่วนของเรา คำตอบสั้นๆ คือ ส่วนใหญ่ไม่ใช่ จากนี้จะเล่าที่มา"

## สไลด์ 2: mark ตัวเล็กตัวเดียว เปลี่ยนความหมายของคำได้

- **บนสไลด์:**
  - **ข่าว** (news) ≠ **ข้าว** (rice) ต่างกันที่ mark ตัวเดียว
  - ตัวชี้วัด OCR ไทยที่ใช้อยู่ (n-gram, edit distance, CER) บอกไม่ได้ว่า mark เป็นปัญหาหรือเปล่า
  - และลงโทษโมเดลที่อ่านคอลัมน์สลับลำดับด้วย
- **ภาพ:** การ์ดตัวอักษร ข่าว / ข้าว ขนาดใหญ่ตรงกลาง ใต้การ์ดมีสามบรรทัดข้างบน (โปรแกรมสไลด์)
- **พูด:** "คนอ่านเห็นทันทีว่าผิด แต่ตัวชี้วัดรวมเห็นเป็นตัวอักษรหนึ่งตัวจากหลายร้อยตัว"

## สไลด์ 3: เมื่อ mark ผิด มีสามคำอธิบาย และต้องแก้ต่างกัน

- **บนสไลด์ (ตาราง 3 แถว):**

| คำอธิบาย                                                   | ถ้าจริง ควรแก้ด้วย                       |
| ---------------------------------------------------------- | ---------------------------------------- |
| หลักฐานในภาพของ mark ขนาดเล็กอ่อน                          | อ่านซ้ำ หรือขยายภาพ                      |
| ความรู้ภาษาของโมเดลทับหลักฐานในภาพ                         | หักความรู้ภาษาออก (contrastive decoding) |
| mark **ไม่ปรากฏใน output เลย** (ข้ามบรรทัด หาไม่เจอ วนซ้ำ) | แก้วิธี decode หรือการหาตำแหน่งข้อความ   |

- **ภาพ:** ตาราง 3 แถว แถวที่สามเน้นด้วยสีส้มเหลืองโปร่ง ใต้ตารางมีบรรทัดเดียว: "งานนี้ถามว่า: ข้อไหนเกิดบ่อยที่สุด"
- **ต้องบอกด้วย:** จาก output อย่างเดียวบอกไม่ได้ว่าในโมเดลเกิดอะไรขึ้น จึงใช้คำว่า "ไม่ปรากฏใน output" ไม่ใช่ "โมเดลมองไม่เห็น" ส่วนร่วมของงาน 3 ข้อ (คะแนน mark ที่ไม่สนลำดับ, วินิจฉัยว่า mark หายที่ไหน, ประเมินวิธี decode ที่ไม่ต้อง train) พูดปากเปล่าจบหน้านี้
- **พูด:** "ก่อนจะแก้อะไร ต้องรู้ก่อนว่า mark หายเพราะเหตุผลข้อไหน"

# ส่วน 2: Related Work (สไลด์ 4–5)

## สไลด์ 4: งานเดิมรายงานความแม่นยำรวม ไม่ได้แยก mark

- **บนสไลด์ (ตาราง 2 แถว):**

| กลุ่มงาน | สิ่งที่ยังไม่มี |
|---|---|
| OCR ภาษาไทยด้วย VLM: ThaiOCRBench, Typhoon OCR, Pathumma, Wayu | ทุกงานรายงานความแม่นยำรวม ไม่มีคะแนนที่แยก mark |
| diacritic ใน OCR: แก้ข้อความหลัง OCR ภาษาเวียดนาม, ประเมิน OCR ภาษาอาหรับ | ไม่พบงานที่ให้คะแนน mark ไทยแยกจากลำดับและข้อความที่เขียนเกิน |

- **ภาพ:** ตาราง 2 แถว 2 คอลัมน์ ช่อง "สิ่งที่ยังไม่มี" ระบายเน้น
- **ต้องบอกด้วย:** งานภาษาอาหรับ (Elsafty et al.) ยังไม่ได้ตรวจต้นฉบับซ้ำว่า "แยกข้อความที่มี diacritic เป็นเงื่อนไขต่างหาก" (`docs/paper/REFERENCE_AUDIT_2026-10-15.md`) ถ้าไม่แน่ใจ พูดแค่ "มีงานด้าน diacritic ในภาษาเวียดนามและอาหรับ"
- **พูด:** "งานเดิมบอกว่าโมเดลเก่งแค่ไหนรวมๆ เรื่อง mark ยังไม่มีคะแนนเฉพาะ"

## สไลด์ 5: วิธีแก้การวนซ้ำมีอยู่แล้ว แต่ไม่มีใครวัดว่าทำ mark เสียเท่าไร

- **บนสไลด์ (ตาราง 2 แถว):**

| กลุ่มงาน | สิ่งที่ยังไม่มี |
|---|---|
| การวนซ้ำและข้อความตกหล่น: Nougat, olmOCR, pipeline ของ PaddleOCR-VL, โค้ด DeepSeek-OCR, CC-OCR | มองการวนซ้ำเป็นสิ่งที่ต้องตรวจจับ ไม่ได้วัดว่าวิธีแก้แต่ละแบบทำ mark ในหน้าที่ไม่วนซ้ำเสียเท่าไร |
| decoding ที่ไม่ต้อง train เพิ่ม: VCD, M3ID, PAI | สมมติว่าความรู้ภาษาเป็นต้นเหตุ แต่กับวรรณยุกต์ไทยเราพบว่ามักถูกอยู่แล้ว |

- **ภาพ:** ตารางเดียวกับหน้า 4 ในรูปแบบเดียวกัน
- **ต้องบอกด้วย:** สิ่งที่เราเพิ่มคือ **การวัด** ไม่ใช่วิธีใหม่ การหยุดเมื่อวนซ้ำมีแนวคิดคล้ายที่ Nougat และ PaddleOCR-VL ใช้อยู่
- **พูด:** "สิ่งที่งานนี้เพิ่มมีสองอย่าง คือวัด mark แยก และวัดว่าวิธีแก้การวนซ้ำแต่ละแบบทำ mark เสียเท่าไร"

# ส่วน 3: วัดอย่างไร และออกแบบงาน (สไลด์ 6–9)

## สไลด์ 6: คะแนน mark ไม่ลงโทษลำดับการอ่าน

- **บนสไลด์:**
  - ให้คะแนน mark ทีละบรรทัดของเฉลย ไม่ว่าบรรทัดนั้นอยู่ตรงไหนของ output
  - ข้อความที่เขียนเกินถูกหักคะแนน
- **ภาพ:** ซ้าย: ตัวอย่างข้อความ 2 บรรทัด เฉลยคือ A แล้ว B แต่โมเดลเขียน B แล้ว A ใต้ภาพ "วิธีเดิม: ผิดเยอะ / วิธีใหม่: ถูกครบ" ขวา: การ์ดตัวเลข "94.9 vs 93.1" กำกับ "Typhoon: ไม่สนลำดับ vs บังคับลำดับ"
- **ต้องบอกด้วย:** ต่างกันราว 2 คะแนนจากลำดับอย่างเดียว ไม่ใช่การอ่านผิด วิธีทำละเอียดอยู่หน้าสำรอง
- **พูด:** "ถ้าโมเดลอ่านกล่องขวาก่อนกล่องซ้ายแต่อ่านถูกทุกตัว ไม่ควรนับว่าผิด"

## สไลด์ 7: ไม่ให้คะแนนกับสำเนาที่เกิดจากการวนซ้ำ

- **บนสไลด์:**
  - สำเนาที่ซ้ำจากการวนซ้ำ **ไม่ได้ recall** แต่ยังถูกหักใน precision
  - โมเดลตั้งต้น: **41.0 → 34.4**
- **ภาพ:** การ์ดตัวเลขใหญ่ "41.0 → 34.4" กำกับ "ราวหนึ่งในหกของ mark ที่ได้คะแนนมาจากสำเนาวนซ้ำ" ใต้การ์ดมีบรรทัดเล็ก "Typhoon: 94.9 → 94.8"
- **ต้องบอกด้วย:** ตรวจแล้วทั้ง 126 ช่วงที่ตัดออกชนขีดจำกัดความยาวทั้งหมด ไม่มีข้อความปกติถูกตัด แบบนี้เพิ่มทีหลังเพราะเพื่อนพบว่า alignment จับสำเนาซ้ำ 434 ชุดไปคู่กับพยางค์ทั่วไปในเฉลย (ชุด calibration)
- **พูด:** "ถ้าไม่ตัดส่วนนี้ โมเดลที่วนซ้ำจะได้คะแนนเกินจริงจากสำเนาที่เขียนซ้ำ"

## สไลด์ 8: ออกแบบงานให้แยก "ปรับวิธี" ออกจาก "ยืนยันผล"

- **บนสไลด์ (เส้นเวลา 3 ช่อง):** **พัฒนา** (ชุด calibration 178 ข้อ) → **ลงทะเบียนล่วงหน้า** (S1, S2, R1) → **เปิดอ่านครั้งเดียว** (ชุด locked 352 ข้อ)
- **ภาพ:** เส้นเวลา 3 ช่อง ช่องที่สามมีกุญแจหรือป้าย "อ่านครั้งเดียว" และเลข 352 ข้อ (โปรแกรมสไลด์)
- **ต้องบอกด้วย:** ชุด locked มี 352 ข้อ ไม่ใช่ราว 415 ที่ registration คาดไว้ ยังไม่ทราบสาเหตุ จึงบอกเป็นจำนวนข้อเท่านั้น ผลทั้งหมดยังเป็นผลเบื้องต้น ไม่ได้เปิดหรือผ่าน gate ใด
- **พูด:** "ชุดแรกใช้ปรับวิธี ชุดที่สองใช้ยืนยันผล ตัวเลขที่อ้างเป็นผลจึงมาจากชุดที่สอง"

## สไลด์ 9: 8 โมเดลที่วัด และการตั้งค่าเดียวกันทุกตัว

- **ต้องบอกด้วย:** generate ใหม่ 8 โมเดลบนข้อใน calibration (185 ข้อที่การตัดเปลี่ยน output และสุ่มอีก 72 ข้อ) ไม่ใช่ชุด locked และ **ยังไม่ได้วัดเวลาจริงที่ประหยัด** ห้ามพูดว่า "ใช้ได้จริงกับข้อมูลที่ไม่เคยเห็นแบบ live" ใช้ GPU T4 2.61 ชั่วโมง
- **พูด:** "การหยุดตอน decode จริงให้ผลตรงกับการตัดทีหลังในทุกข้อที่ตรวจ"

# ส่วน 7: อันดับ ข้อจำกัด สรุป (สไลด์ 23–27)

## สไลด์ 23: Typhoon แข็งที่สุดที่วัด แต่แยกจาก Pathumma ไม่ออก

- **บนสไลด์ (ตาราง 3 แถว):** "Typhoon เหนือ 6 โมเดลอื่น ทั้งสองงาน" ✔ · "Typhoon vs Pathumma: ไม่พบความต่าง" ≈ · "ตัวเลข locked ต่ำกว่า calibration (92.6 vs 94.9)" ลูกศรลง
- **ภาพ:** ตาราง 3 แถว (โปรแกรมสไลด์)
- **ต้องบอกด้วย:** Typhoon − Pathumma (prompt ของ card) อ่านทั้งหน้า +1.5 [−3.1, +6.5] อ่านข้อความสั้น +9.0 [−3.6, +21.3] ที่ n = 128 และ 224 ครึ่งความกว้างของช่วงราว ±6 และ ±13 จุด จึงไม่ใช่ "เท่ากัน" ตัวอย่างที่เหนือ: Typhoon − Wayu +19.0, Typhoon − DeepSeek-OCR-2 +57.2 บนหน้าเต็ม ต้องมีหมายเหตุติดตัวเลข Typhoon และ Pathumma ทุกตัว (Typhoon มาจากกลุ่มที่ทำ benchmark, Pathumma ไม่ระบุข้อมูลฝึก) และตัวเลข locked ของ Typhoon (92.6 / 73.7) ต่ำกว่า calibration (94.9 / 81.7) ซึ่งเป็นปกติบนข้อมูลที่ไม่เคยปรับ จึงอ้างตัวเลข locked
- **พูด:** "Typhoon ได้คะแนนสูงกว่าหกโมเดล เทียบกับ Pathumma ข้อมูลยังไม่พอจะบอกว่าใครนำ"

## สไลด์ 24: ข้อจำกัด (1): ขอบเขต

- **บนสไลด์ (3 ข้อสั้น):** benchmark เดียว สองงาน · 8 โมเดลตามที่เผยแพร่ (visual token ไม่เท่ากัน) · ข้อสรุปเป็นเรื่องกลไก ไม่ใช่อัตรา
- **ภาพ:** รายการ 3 ข้อ ใช้สีน้ำเงินกับเทาเท่านั้น
- **ต้องบอกด้วย:** โมเดลอ่านทีละกรอบสองตัวถูกนำมาอ่านทั้งหน้าเกินกว่าที่ออกแบบไว้ DeepSeek-OCR-2 รัน fp16 อย่างเดียว output ที่วนซ้ำของ Typhoon และ Pathumma มีน้อย ช่วงความเชื่อมั่นส่วนใหญ่จึงรวมศูนย์ไว้
- **พูด:** "ผลนี้ใช้กับ 8 โมเดลนี้บน benchmark นี้ อ้างไปไกลกว่านั้นไม่ได้"

## สไลด์ 25: ข้อจำกัด (2): การออกแบบและการตีความ

- **บนสไลด์ (4 ข้อสั้น):** กฎการหยุดและตัวชี้วัดเขียนหลังเห็น calibration · S1 ตามที่ลงทะเบียนไม่ผ่านเพราะหนึ่งเซลล์ · "ไม่ปรากฏใน output" ≠ "อ่านไม่ได้" · forced choice แสดงว่าโมเดลรู้อะไร ไม่ใช่ทำอะไรตอนเขียน
- **ภาพ:** รายการ 4 ข้อ
- **ต้องบอกด้วย:** การหยุดบนชุด locked ทำแบบ offline การจัดสาเหตุเป็นแบบอัตโนมัติ ผลทั้งหมดเป็นผลเบื้องต้น (`PRELIMINARY_PILOT_NOT_GATE_EVIDENCE`) ไม่ได้เปิดหรือผ่าน gate ใด
- **พูด:** "ข้อจำกัดที่เหลือคือกฎการหยุดเขียนหลังเห็นข้อมูลชุดแรก และข้อความที่ไม่ปรากฏยังไม่เท่ากับอ่านไม่ได้"

## สไลด์ 26: สรุป: ส่วนใหญ่ไม่ใช่ จุดอ่อนอยู่ที่ข้อความไม่ถูกเขียนออกมา

- **บนสไลด์ (การ์ดตัวเลข 3 ใบ):** "4.7–15.8 เท่า" ข้อความที่ไม่ปรากฏเสียมากกว่าอ่านผิด · "~99%" วรรณยุกต์ถูกเมื่อให้บริบทถูก (Thai fine-tune) · "12 / 13" เซลล์ที่การหยุดเพิ่มคะแนน
- **ภาพ:** การ์ดตัวเลข 3 ใบ ตัวเลขสีส้มเหลือง
- **ต้องบอกด้วย:** Qwen3-VL-4B รู้เท่ากันแต่เขียนผิดบ้าง การหักความรู้ภาษาออกไม่ใช่ทางแก้ ผลทั้งหมดมาจาก benchmark เดียว
- **พูด:** "คำตอบของคำถามตอนต้น: ส่วนใหญ่ไม่ใช่ จุดอ่อนอยู่ที่ข้อความไม่ถูกเขียนออกมา"

## สไลด์ 27: ขั้นต่อไป (ยังไม่ได้ทำ)

- **บนสไลด์ (3 ข้อ):** แยก "เห็นแล้วข้าม" ออกจาก "อ่านไม่ออกจริง" ด้วยการวัดระดับบรรทัด · ทดสอบบน benchmark ที่สอง · วัดเวลาจริงของการหยุดตอน decode
- **ภาพ:** รายการ 3 ข้อ และบรรทัด "ขอบคุณ · คำถาม"
- **ต้องบอกด้วย:** ขั้นต่อไปเป็นแผน ไม่ใช่ผลที่ทำแล้ว
- **พูด:** "ขั้นต่อไปที่อยากทำที่สุดคือแยกว่าข้อความที่หายเกิดจากมองไม่เห็นหรือเห็นแล้วไม่เขียน"

ชื่อไฟล์ใช้เลขสไลด์ใน `docs/paper/SLIDES_CONTENT.md` นำหน้า สร้างด้วย `scripts/slides_make_charts.py`:

```bash
uv run --with plotly --with kaleido python scripts/slides_make_charts.py
```

ใส่ `--only s19` เพื่อทำรูปเดียว หรือ `--svg` เพื่อได้ SVG ด้วย (ถ้าสั่งทั้งชุดแล้วค้าง ให้รันทีละรูป)

**ฟอนต์:** กราฟใช้ลำดับ Noto Sans Thai → Leelawadee UI → Tahoma เครื่องนี้ไม่ได้ติดตั้ง Noto Sans Thai กราฟจึงใช้ Leelawadee UI ซึ่งวางสระและวรรณยุกต์ซ้อนถูกต้อง (ซูมดูแล้ว) ถ้าติดตั้ง Noto แล้วรันสคริปต์ใหม่ จะใช้ Noto ทันที ตัวหนาของ Noto ไม่มีใน repository

**ขนาดฟอนต์ในรูป:** คิดที่ 1 px = 0.6 pt บนสไลด์กว้าง 1600 px (ตัวเลข 18 pt, ป้าย 14 pt) ถ้าวางรูปเล็กกว่าขนาดที่ระบุ ตัวอักษรจะเล็กลงตามสัดส่วน
