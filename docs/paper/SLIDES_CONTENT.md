## เรื่องที่เล่าทั้งเด็ค (เส้นเรื่องเดียว)

> วรรณยุกต์และสระของไทยตัวเล็กและเปลี่ยนความหมายคำได้ คนจึงสงสัยว่าเป็นจุดอ่อนของ OCR ภาษาไทย เราวัดใน 8 โมเดลแบบเปิดแล้วพบว่า **ส่วนใหญ่ไม่ใช่** mark ที่เสียไปส่วนใหญ่ไม่ได้ถูกอ่านผิด แต่ **ไม่ปรากฏใน output เลย** (อาจเป็นการข้ามบรรทัด หาไม่เจอ หรือวนซ้ำ ซึ่งยังแยกสามกรณีนี้ไม่ได้) เมื่อให้บริบทถูก โมเดลเลือกวรรณยุกต์ถูกราว 99% ส่วนวิธีที่ช่วยได้ง่ายที่สุดคือหยุดเมื่อวนซ้ำ ซึ่งยืนยันบนชุดข้อมูลที่เปิดอ่านครั้งเดียว

## ก่อนเริ่ม: ตกลงคำที่ใช้ทั้ง deck

| คำ                        | ความหมาย                                                                                                                             |
| ------------------------- | ------------------------------------------------------------------------------------------------------------------------------------ |
| **mark**                  | สระบน (ิ ี ึ ื ั ็), สระล่าง (ุ ู) และวรรณยุกต์ (่ ้ ๊ ๋)                                                                            |
| **คะแนน mark**            | เอา mark ทุกตัวในเฉลยมาเทียบกับที่โมเดลเขียน หักทั้งตัวที่หายและตัวที่เขียนเกิน เต็ม 100 (ชื่อทางเทคนิคคือ mark F1) ไม่สนลำดับบรรทัด |
| **ไม่ปรากฏใน output**     | บรรทัดหรือช่วงข้อความในเฉลยที่หาไม่เจอในสิ่งที่โมเดลเขียน **ไม่ได้แปลว่าโมเดลมองไม่เห็น** (อาจเห็นแล้วไม่เขียน)                      |
| **วนซ้ำ (loop)**          | โมเดลเขียนหน่วยเดิมซ้ำไม่หยุดจนถึงความยาวสูงสุด                                                                                      |
| **หยุดเมื่อวนซ้ำ (stop)** | ตัด output ตั้งแต่สำเนาแรกของหน่วยที่ซ้ำ 8 ครั้ง (หรือ 6 ครั้งถ้าหน่วยยาว 50 ตัวอักษรขึ้นไป) ไม่ต้อง train เพิ่ม                     |
| **ชุดปรับวิธี**       | 178 ข้อ (อ่านทั้งหน้า 69, อ่านข้อความสั้น 109) ใช้พัฒนาวิธีและตัดสินใจออกแบบ                                                         |
| **ชุดที่ล็อกไว้**            | 352 ข้อ (อ่านทั้งหน้า 128, อ่านข้อความสั้น 224) ไม่แตะจนกฎทุกข้อนิ่ง แล้วเปิดอ่าน **ครั้งเดียว** ตามที่ลงทะเบียนไว้ล่วงหน้า          |
| **forced choice**         | ให้ข้อความที่ถูกต้องจนถึงตำแหน่ง mark แล้วให้โมเดลให้คะแนนตัวเลือก mark ที่เป็นไปได้ ไม่ใช่การเขียนเอง                               |
| **Thai fine-tune**        | Typhoon OCR 1.5 และ Pathumma-llm-vision 3.0 (ทั้งคู่ train ต่อจาก Qwen3-VL-2B)                                                       |
| **โมเดลทั่วไป**           | Qwen3-VL-2B (ตั้งต้น), Qwen3-VL-4B, SEA-LION v4 4B                                                                                   |

**ป้ายเล็กมุมล่างทุกหน้าที่มีผล (สองแบบ):**
- ผลบนชุดปรับวิธี: "ผลเบื้องต้น · ชุดปรับวิธี (ใช้ออกแบบวิธี)"
- ผลบนชุดที่ล็อกไว้: "ผลเบื้องต้น · ชุดที่ล็อกไว้ อ่านครั้งเดียว · ไม่ใช่หลักฐานผ่าน gate"

**ถ้ามีทั้งตัวเลข ชุดปรับวิธี และ ชุดที่ล็อกไว้ ให้ใช้ ชุดที่ล็อกไว้ เป็นตัวเลขหลัก**

# ส่วน 1: ชื่อเรื่อง และ Introduction (สไลด์ 1–3)

## สไลด์ 1: ชื่อเรื่อง

- **บนสไลด์:** *Are Tone Marks the Weak Point of Open Thai OCR? A Locked-Split Study of Eight Models* / "วรรณยุกต์เป็นจุดอ่อนของ OCR ภาษาไทยแบบเปิดจริงหรือ" / ผู้เขียน 3 คนและสังกัด / 
- **พูด:** "วันนี้เราจะเล่างานที่ถามว่า วรรณยุกต์เป็นจุดอ่อนของ OCR ภาษาไทยแบบเปิดจริงหรือไม่ งานนี้ทำร่วมกับเพื่อน (PELY334) เพื่อนรันการทดลองบน GPU ส่วนวิธีวัดและการเขียน paper เราทำเอง คำตอบสั้นๆ คือ ส่วนใหญ่ไม่ใช่ เดี๋ยวเล่าที่มา"

## สไลด์ 2: mark ตัวเล็กตัวเดียว เปลี่ยนความหมายของคำได้

- **บนสไลด์:**
  - **ข่าว** (news) ≠ **ข้าว** (rice) ต่างกันที่ mark ตัวเดียว
  - ตัวชี้วัด OCR ไทยที่ใช้อยู่ (n-gram, edit distance, CER) บอกไม่ได้ว่า mark เป็นปัญหาหรือเปล่า
  - และลงโทษโมเดลที่อ่านคอลัมน์สลับลำดับด้วย
- **ภาพ:** การ์ดตัวอักษร ข่าว / ข้าว ขนาดใหญ่ตรงกลาง ใต้การ์ดมีสามบรรทัดข้างบน (โปรแกรมสไลด์)
- **พูด:** "ลองดูคำว่า ข่าว กับ ข้าว ต่างกันที่ mark ตัวเดียว คนอ่านเห็นทันทีว่าผิด แต่ตัวชี้วัดที่ใช้กันอยู่เห็นเป็นตัวอักษรหนึ่งตัวจากหลายร้อยตัว และยังหักคะแนนเมื่อโมเดลอ่านคอลัมน์สลับลำดับด้วย"

## สไลด์ 3: เมื่อ mark ผิด มีสามคำอธิบาย และต้องแก้ต่างกัน

- **บนสไลด์ (ตาราง 3 แถว):**

| คำอธิบาย                                                   | ถ้าจริง ควรแก้ด้วย                       |
| ---------------------------------------------------------- | ---------------------------------------- |
| หลักฐานในภาพของ mark ขนาดเล็กอ่อน                          | อ่านซ้ำ หรือขยายภาพ                      |
| ความรู้ภาษาของโมเดลทับหลักฐานในภาพ                         | หักความรู้ภาษาออก (contrastive decoding) |
| mark **ไม่ปรากฏใน output เลย** (ข้ามบรรทัด หาไม่เจอ วนซ้ำ) | แก้วิธี decode หรือการหาตำแหน่งข้อความ   |

- **ภาพ:** ตาราง 3 แถว แถวที่สามเน้นด้วยสีส้มเหลืองโปร่ง ใต้ตารางมีบรรทัดเดียว: "งานนี้ถามว่า: ข้อไหนเกิดบ่อยที่สุด"
- **ต้องบอกด้วย:** จาก output อย่างเดียวบอกไม่ได้ว่าในโมเดลเกิดอะไรขึ้น จึงใช้คำว่า "ไม่ปรากฏใน output" ไม่ใช่ "โมเดลมองไม่เห็น" ส่วนร่วมของงาน 3 ข้อ (คะแนน mark ที่ไม่สนลำดับ, วินิจฉัยว่า mark หายที่ไหน, ประเมินวิธี decode ที่ไม่ต้อง train) พูดปากเปล่าจบหน้านี้
- **พูด:** "ถ้า mark ผิด อธิบายได้สามทาง ภาพอาจเล็กและอ่อนจนอ่านไม่ออก ความรู้ภาษาอาจทับสิ่งที่เห็น หรือ mark ไม่ถูกเขียนออกมาเลย แต่ละทางแก้ไม่เหมือนกัน เราจึงต้องรู้ก่อนว่าข้อไหนเกิดบ่อยที่สุด งานนี้ทำสามอย่าง คือคะแนน mark ที่ไม่สนลำดับ วัดว่า mark หายที่ไหน และประเมินวิธี decode ที่ไม่ต้อง train เพิ่ม"

# ส่วน 2: Related Work (สไลด์ 4–5)

## สไลด์ 4: Related Work: งานเดิมรายงานความแม่นยำรวม ไม่ได้แยก mark

- **บนสไลด์ (ตาราง 2 แถว):**

| กลุ่มงาน | สิ่งที่ยังไม่มี |
|---|---|
| OCR ภาษาไทยด้วย VLM: ThaiOCRBench, Typhoon OCR, Pathumma, Wayu | ทุกงานรายงานความแม่นยำรวม ไม่มีคะแนนที่แยก mark |
| diacritic ใน OCR: แก้ข้อความหลัง OCR ภาษาเวียดนาม, ประเมิน OCR ภาษาอาหรับ | ไม่พบงานที่ให้คะแนน mark ไทยแยกจากลำดับและข้อความที่เขียนเกิน |

- **ภาพ:** ตาราง 2 แถว 2 คอลัมน์ ช่อง "สิ่งที่ยังไม่มี" ระบายเน้น
- **ต้องบอกด้วย:** งานภาษาอาหรับ (Elsafty et al.) ยังไม่ได้ตรวจต้นฉบับซ้ำว่า "แยกข้อความที่มี diacritic เป็นเงื่อนไขต่างหาก" (`docs/paper/REFERENCE_AUDIT_2026-10-15.md`) ถ้าไม่แน่ใจ พูดแค่ "มีงานด้าน diacritic ในภาษาเวียดนามและอาหรับ"
- **พูด:** "งาน OCR ภาษาไทยด้วย VLM ที่มีอยู่รายงานความแม่นยำรวม ยังไม่มีงานที่ให้คะแนน mark แยก ส่วนงานด้าน diacritic ในภาษาเวียดนามและอาหรับมีอยู่ แต่เรายังไม่พบงานที่ให้คะแนน mark ไทยแยกจากลำดับและข้อความที่เขียนเกิน"

## สไลด์ 5: Related Work: มีวิธีแก้การวนซ้ำแล้ว แต่ยังไม่พบงานที่วัดผลต่อ mark

- **บนสไลด์ (ตาราง 2 แถว):**

| กลุ่มงาน | สิ่งที่ยังไม่มี |
|---|---|
| การวนซ้ำและข้อความตกหล่น: Nougat, olmOCR, pipeline ของ PaddleOCR-VL, โค้ด DeepSeek-OCR, CC-OCR | มองการวนซ้ำเป็นสิ่งที่ต้องตรวจจับหรือหลีกเลี่ยง ยังไม่พบงานที่วัดผลของวิธีแก้ต่อ mark ในหน้าที่ไม่วนซ้ำ |
| decoding ที่ไม่ต้อง train เพิ่ม: VCD, M3ID, PAI | สมมติว่าความรู้ภาษาเป็นต้นเหตุ แต่กับวรรณยุกต์ไทยเราพบว่ามักถูกอยู่แล้ว |

- **ภาพ:** ตารางเดียวกับหน้า 4 ในรูปแบบเดียวกัน
- **ต้องบอกด้วย:** สิ่งที่เราเพิ่มคือ **การวัด** ไม่ใช่วิธีใหม่ การหยุดเมื่อวนซ้ำมีแนวคิดคล้ายที่ Nougat และ PaddleOCR-VL ใช้อยู่
- **พูด:** "เรื่องการวนซ้ำ มีหลายงานแก้ไว้แล้ว แต่มองเป็นสิ่งที่ต้องตรวจจับหรือหลีกเลี่ยง เรายังไม่พบงานที่วัดว่าวิธีแก้แต่ละแบบทำให้ mark ในหน้าที่ไม่วนซ้ำเสียเท่าไร สิ่งที่งานนี้เพิ่มจึงมีสองอย่าง คือวัด mark แยก และวัดผลของวิธีแก้การวนซ้ำต่อ mark"

# ส่วน 3: วัดอย่างไร และออกแบบงาน (สไลด์ 6–9)

## สไลด์ 6: คะแนน mark ไม่ลงโทษลำดับการอ่าน

- **บนสไลด์:**
  - ให้คะแนน mark ทีละบรรทัดของเฉลย ไม่ว่าบรรทัดนั้นอยู่ตรงไหนของ output
  - ข้อความที่เขียนเกินถูกหักคะแนน
- **ภาพ:** ซ้าย: ตัวอย่างข้อความ 2 บรรทัด เฉลยคือ A แล้ว B แต่โมเดลเขียน B แล้ว A ใต้ภาพ "วิธีเดิม: ผิดเยอะ / วิธีใหม่: ถูกครบ" ขวา: การ์ดตัวเลข "94.9 vs 93.1" กำกับ "Typhoon อ่านทั้งหน้า: ไม่สนลำดับ vs บังคับลำดับ"
- **ต้องบอกด้วย:** ต่างกันราว 2 คะแนนจากลำดับอย่างเดียว ไม่ใช่การอ่านผิด วิธีทำละเอียดอยู่หน้าสำรอง
- **พูด:** "ข้อแรกของวิธีวัด คะแนน mark ดูทีละบรรทัดของเฉลยว่าอยู่ตรงไหนของ output ก็ได้ ถ้าโมเดลอ่านกล่องขวาก่อนกล่องซ้ายแต่ถูกทุกตัว เราไม่นับว่าผิด ตัวอย่างคือ Typhoon ได้ 94.9 เมื่อไม่สนลำดับ และ 93.1 เมื่อบังคับลำดับ"

## สไลด์ 7: ไม่ให้คะแนนกับสำเนาที่เกิดจากการวนซ้ำ

- **บนสไลด์:**
  - สำเนาที่ซ้ำจากการวนซ้ำ **ไม่ได้ recall** แต่ยังถูกหักใน precision
  - โมเดลตั้งต้น: **41.0 → 34.4**
- **ภาพ:** การ์ดตัวเลขใหญ่ "41.0 → 34.4" กำกับ "ราวหนึ่งในหกของ mark ที่ได้คะแนนมาจากสำเนาวนซ้ำ" ใต้การ์ดมีบรรทัดเล็ก "Typhoon: 94.9 → 94.8"
- **ต้องบอกด้วย:** ตรวจแล้วทั้ง 126 ช่วงที่ตัดออกชนขีดจำกัดความยาวทั้งหมด ไม่มีข้อความปกติถูกตัด แบบนี้เพิ่มทีหลังเพราะเพื่อนพบว่า alignment จับสำเนาซ้ำ 434 ชุดไปคู่กับพยางค์ทั่วไปในเฉลย (ชุดปรับวิธี)
- **พูด:** "ข้อที่สอง สำเนาที่เกิดจากการวนซ้ำไม่ได้คะแนน แต่ยังถูกหักใน precision ถ้าไม่ตัดส่วนนี้ โมเดลที่วนซ้ำจะได้คะแนนเกินจริง ในโมเดลตั้งต้นคะแนนลดจาก 41.0 เป็น 34.4 ส่วน Typhoon แทบไม่เปลี่ยน"

## สไลด์ 8: ออกแบบงานให้แยก "ปรับวิธี" ออกจาก "ยืนยันผล"

- **บนสไลด์ (เส้นเวลา 3 ช่อง):** **พัฒนาวิธี** (ข้อสอบชุดปรับวิธี 178 ข้อ) → **จดเกณฑ์ไว้ก่อนดูผล** (ตั้งเกณฑ์ผ่าน/ไม่ผ่าน 3 ข้อ) → **เปิดดูผลครั้งเดียว** (ข้อสอบชุดที่ล็อกไว้ 352 ข้อ)
- **ภาพ:** เส้นเวลา 3 ช่อง ช่องที่สามมีกุญแจหรือป้าย "เปิดดูผลครั้งเดียว" และเลข 352 ข้อ (โปรแกรมสไลด์)
- **ต้องบอกด้วย:** "จดเกณฑ์ไว้ก่อนดูผล" (เดิมเรียก "ลงทะเบียนล่วงหน้า") คือเขียนเกณฑ์ผ่าน/ไม่ผ่านสามข้อ (S1, S2, R1) ไว้ก่อนเปิดชุดที่ล็อกไว้ เพื่อไม่ให้เกณฑ์ขยับตามผล รหัส S1, S2, R1 อยู่ที่สไลด์ 18 ชุดที่ล็อกไว้ 352 ข้อ (66%) และ ชุดปรับวิธี 178 ข้อ (34%) จากข้อสอบ 530 ข้อ แบ่งตามงานและหมวดโดยปัดขึ้นต่อหมวด ตัวเลข "ราว 415" ใน registration เป็นการประมาณที่ผิด ไม่มีข้อใดถูกตัดออก ผลทั้งหมดยังเป็นผลเบื้องต้น ไม่ได้เปิดหรือผ่าน gate ใด
- **พูด:** "เราแบ่งข้อสอบเป็นสองชุด ชุดปรับวิธี 178 ข้อ ใช้ลองและปรับวิธีได้เต็มที่ ก่อนจะเปิดอีกชุด เราจดเกณฑ์ผ่านหรือไม่ผ่านสามข้อไว้ก่อนดูผล เพื่อไม่ให้เกณฑ์ขยับตามผลที่ออกมา แล้วจึงเปิดชุดที่ล็อกไว้ 352 ข้อ อ่านผลครั้งเดียว ตัวเลขที่เราอ้างเป็นผลจึงมาจากชุดที่สาม"

## สไลด์ 9: 8 โมเดลที่วัด และการตั้งค่าเดียวกันทุกตัว

- **บนสไลด์:** ชื่อโมเดล 8 ตัว (ตาราง 4×2): Typhoon OCR 1.5, Pathumma 3.0, Wayu, PaddleOCR-VL-1.6, Qwen3-VL-2B, Qwen3-VL-4B, SEA-LION v4 4B, DeepSeek-OCR-2 / ใต้ตาราง 1 บรรทัด: "greedy · fp16 · token ใหม่ไม่เกิน 3,072 · GPU T4"

## สไลด์ 12: ข้อความที่ไม่ปรากฏทำให้เสีย mark มากกว่าการอ่านผิด 7–12 เท่า

- **บนสไลด์ (การ์ดตัวเลข 3 ใบ):** "3.2% / 9.3% / 29–44%" = mark ที่เสียเพราะข้อความไม่ปรากฏ (Typhoon / Pathumma / อีกสี่ตัว) · "0.4% / 0.8% / 2.7–4.3%" = เสียเพราะอ่านผิดทั้งที่พยัญชนะถูก · "7–12 เท่า" ตัวใหญ่สีส้มเหลือง
- **ภาพ:** การ์ดตัวเลข 3 ใบ (โปรแกรมสไลด์)
- **ต้องบอกด้วย:** บรรทัดที่หายของ Typhoon ส่วนใหญ่คือข้อความใน infographic กราฟ โฆษณาแทรก และชื่อเรื่อง สำหรับโมเดลที่วนซ้ำ บรรทัดหลังการวนซ้ำนับเป็น "หาย" แยกไม่ได้ว่าเพราะวนซ้ำหรือเพราะโมเดลไม่อ่านอยู่แล้ว และ "ไม่ปรากฏ" ไม่เท่ากับ "อ่านไม่ได้" (ผลบนชุดปรับวิธี) มีหลักฐานทางอ้อมจากงานนำร่องของเพื่อน (Track C): ใน task Fine-grained ที่คำถามบอกกรอบไว้ (task คนละอันกับสองงานของ deck นี้ ชุดปรับวิธี 69 ข้อ) Typhoon ตอบด้วยข้อความในกรอบ 7.2% เมื่อได้ภาพทั้งหน้า 33.3% เมื่อตัดประโยคที่บอกระบบพิกัดออกจากคำถาม และ 98.6% เมื่อได้เฉพาะภาพตัด แปลว่าข้อความที่ไม่ปรากฏเมื่อได้ภาพทั้งหน้า อย่างน้อยบางส่วนเป็นข้อความที่โมเดลอ่านได้เมื่อได้ภาพตัด แต่ตัวคำถามก็เป็นส่วนของปัญหา (7.2% → 33.3% เมื่อแก้แค่ประโยคเดียว) จึงยังแยกไม่ได้ว่าเป็นการหาตำแหน่งไม่เจอหรือทำตามคำถามไม่ได้ และยังไม่รู้ว่าอธิบายบรรทัดที่หายตอนถอดทั้งหน้าได้กี่ส่วน (โมเดลเดียว ไม่ใช่ถอดทั้งหน้า) ในข้อที่ตอบจากภาพทั้งหน้าได้ ภาพตัดไม่ได้แก้ mark ใดให้ถูกเพิ่ม (วรรณยุกต์ 29 จาก 30 ถูกทั้งสองแบบ ภาพตัดทำผิดเพิ่ม 1) แต่เป็นกลุ่มที่เลือกมา (กรอบใหญ่กว่า) จึงเป็นข้อที่ง่ายกว่า
- **พูด:** "ถ้านับเป็นตัวเลข mark ที่เสียเพราะข้อความไม่ปรากฏ มากกว่า mark ที่เสียเพราะอ่านผิดทั้งที่พยัญชนะถูก 7 ถึง 12 เท่า นี่เป็นผลหลักของงาน และสไลด์ 21 ยืนยันกับข้อมูลชุดที่ไม่เคยใช้"

- **บนสไลด์ (ตาราง 3 แถว):**

- **พูด:** "เซลล์ที่ไม่ผ่านคือ Pathumma อ่านทั้งหน้า ได้ +1.3 ช่วง 95% [0.0, +3.5] เกณฑ์ที่ลงทะเบียนคือทุกเซลล์ต้องผ่าน S1 จึงไม่ผ่านตามที่ลงทะเบียน ผ่าน 12 จาก 13 ไม่ครบ Pathumma วนซ้ำแค่ 4 จาก 128 หน้า จึงมีอะไรให้แก้น้อย ส่วน S2 ผ่าน การหยุดเปลี่ยน output ที่จบเองเพียง 1 จาก 2,400 รายการ"

## สไลด์ 23: Typhoon แข็งที่สุดที่วัด แต่แยกจาก Pathumma ไม่ออก

- **บนสไลด์ (ตาราง 3 แถว):** "Typhoon เหนือ 6 โมเดลอื่น ทั้งสองงาน" ✔ · "Typhoon vs Pathumma: ไม่พบความต่าง" ≈ · "ตัวเลขชุดที่ล็อกไว้ต่ำกว่าชุดปรับวิธี (92.6 vs 94.9)" ลูกศรลง
- **ภาพ:** ตาราง 3 แถว (โปรแกรมสไลด์)
- **ต้องบอกด้วย:** Typhoon − Pathumma (prompt ของ card) อ่านทั้งหน้า +1.5 [−3.1, +6.5] อ่านข้อความสั้น +9.0 [−3.6, +21.3] ที่ n = 128 และ 224 ครึ่งความกว้างของช่วงราว ±6 และ ±13 จุด จึงไม่ใช่ "เท่ากัน" ตัวอย่างที่เหนือ: Typhoon − Wayu +19.0, Typhoon − DeepSeek-OCR-2 +57.2 บนหน้าเต็ม ต้องมีหมายเหตุติดตัวเลข Typhoon และ Pathumma ทุกตัว (Typhoon มาจากกลุ่มที่ทำ benchmark, Pathumma ไม่ระบุข้อมูลฝึก) และตัวเลข ชุดที่ล็อกไว้ ของ Typhoon (92.6 / 73.7) ต่ำกว่าชุดปรับวิธี (94.9 / 81.7) ซึ่งเป็นปกติบนข้อมูลที่ไม่เคยปรับ จึงอ้างตัวเลข ชุดที่ล็อกไว้ อ่านข้อความสั้นของ Typhoon (73.7) ต่ำกว่าอ่านทั้งหน้า (92.6) มาก: หลังหยุดเมื่อวนซ้ำ recall 76.5% และ precision 77.9% (Pathumma recall ราว 95% แต่ precision ต่ำกว่ามาก) งานนี้ถามส่วนหนึ่งของหน้า ไม่ได้ทดสอบว่าเพราะอะไร และผลของงานนำร่อง Fine-grained (สไลด์ 12) เป็น task อื่น ใช้อธิบายตัวเลขนี้ไม่ได้
- **พูด:** "Typhoon ได้คะแนนสูงกว่าหกโมเดลอื่นทั้งสองงาน เทียบกับ Pathumma ข้อมูลยังไม่พอจะบอกว่าใครนำ ตัวเลขบนชุดที่ล็อกไว้ ต่ำกว่าชุดปรับวิธี ซึ่งเกิดได้กับข้อมูลที่ไม่เคยปรับ เราจึงอ้างตัวเลขของชุดที่ล็อกไว้"

- **พูด:** "ขั้นต่อไปที่อยากทำที่สุดคือแยกว่าข้อความที่หายเกิดจากมองไม่เห็นหรือเห็นแล้วไม่เขียน งานนำร่องของเพื่อนให้สัญญาณทางอ้อมแล้ว แต่เป็นโมเดลเดียวและเป็นงานที่ให้กรอบ เราจึงต้องวัดระดับบรรทัดตอนถอดทั้งหน้า จากนั้นทดสอบบน benchmark ที่สอง และวัดเวลาจริงของการหยุดตอน decode ทั้งสามข้อยังเป็นแผน ขอบคุณ"
